==================================================
APPROVED FOUNDATION
==================================================

Implement the minimum server-side canonical posting foundation:

1. One consequential accounting command boundary.
2. Normalized canonical journal header and journal-line model.
3. Server-side double-entry and money invariants.
4. Source/company/posting-context/economic-effect identity.
5. Final source-freshness revalidation.
6. Immutable posted journals.
7. Additive linked corrections/reversals.
8. Durable idempotency and concurrency protection.
9. Atomic journal + source/effect + audit persistence.
10. Required unit, integration, transaction, concurrency, authorization and
    company-isolation evidence.

Later accounting workflows must call this authority and must not bypass it.

==================================================
BL-01-FI
==================================================

Reuse the completed BL-01-FI Principal and Tenant Guard.

Do NOT create a parallel membership/company authorization mechanism.

Every consequential command must establish:

- authenticated actor or validated job principal;
- one authoritative company;
- active membership or approved system/job context;

Malformed, conflicting, revoked, missing or ambiguous authorization context
must fail closed.

==================================================
POSTING AUTHORITY
==================================================

Only the new canonical posting authority may create canonical journals.

Do not permit canonical journal creation through:

- generic CRUD;
- browser state;
- AI output;
- imports;
- queue payloads;
- retries;
- direct client journal-line creation.

Server-side values are authoritative.

Client/browser totals are never authoritative.

==================================================
ACCOUNTING INVARIANTS
==================================================

Enforce at minimum:

- at least two journal lines;
- total debit equals total credit;
- positive total debit/credit;
- integer non-negative minor units;
- debit and credit cannot both be positive on one line;
- valid active account;
- account belongs to the correct company;
- all lines belong to the same journal/company/currency;
- valid posting date;
- exactly one financial year;
- valid accounting period;
- closed periods reject ordinary posting;
- valid configuration context;
- valid source/effect identity;
- no duplicate economic effect;
- no partial canonical accounting effect.

Posted journals and posted lines are immutable.

==================================================
SOURCE FRESHNESS
==================================================

Implement the existing source-freshness/posting-safety contract.

Before canonical persistence, revalidate authoritative current state.

Where available use:

- source revision/event sequence/provider token;
- otherwise the approved normalized evidence hash fallback.

Revalidate:

- source ownership;
- source identity;
- revision/evidence;
- source status;
- company context;
- actor/job;
- membership;
- capability;
- posting date;
- financial year;
- accounting period/state;
- DEC-11 configuration version;
- DEC-10 mapping/account eligibility;
- VAT context where applicable;
- economic-effect identity;
- canonical journal invariants.

Never post from an old browser/AI/queue/draft envelope.

If freshness cannot be established, reject or route according to the approved contract.

Do not assign source freshness to DEC-12.

==================================================
IDEMPOTENCY / CONCURRENCY
==================================================

Implement durable company-scoped economic-effect identity.

Required behavior:

- same identity + same meaning = original result;
- same identity + different meaning = explicit conflict;
- concurrent first attempts = one accounting effect;
- retry = safe;
- uncertain outcome = resolve using the same identity;
- duplicate reversal/correction = safe duplicate handling;
- never create a second identity merely because a request timed out.

Do not claim that a timeout means "not posted".

Provide safe result lookup or equivalent uncertain/pending handling.

==================================================
CORRECTIONS / REVERSALS
==================================================

Preserve original posted journals.

Corrections/reversals must be additive, balanced and linked.

Never edit or delete the original posted journal.

Do not reopen periods or create year-end closing journals automatically.

If the exact correction/reversal implementation requires a genuine policy
decision rather than an engineering choice:

STOP and report the conflict.

Do not invent accounting policy.

==================================================
ATOMICITY / AUDIT
==================================================

Where the storage boundary permits, the following must commit atomically:

- journal;
- journal lines;
- source/effect relationship;
- economic-effect/idempotency result;
- required successful audit evidence.

If a mandatory validation fails, no accounting effect is permitted.

If canonical persistence fails, no partial journal may remain.

If required successful-post audit persistence fails, no successful accounting
effect may remain.

Rejected/stale/conflict/uncertain outcomes must not create accounting effects.

==================================================
TESTING REQUIREMENTS
==================================================

Before completion, prove at minimum:

ACCOUNTING

- balanced posting succeeds;
- unbalanced posting fails;
- zero journal fails;
- invalid monetary values fail;
- invalid account fails;
- wrong-company account fails;
- mixed company/currency fails.

AUTHORIZATION

- inactive membership fails;
- revoked membership fails;
- insufficient capability fails;
- malformed context fails;
- conflicting company context fails;
- Company A cannot access/post using Company B resources.

PERIOD / CONFIGURATION

- invalid period fails;
- closed period fails;
- valid period succeeds;
- configuration mismatch fails;
- valid configuration resolves correctly.

FRESHNESS

- stale revision fails;
- stale evidence hash fails;
- missing/ambiguous source fails;
- changed context between analysis and posting fails.

IDEMPOTENCY

- duplicate effect produces one journal;
- same identity returns original result;
- conflicting identity meaning fails;
- concurrent requests cannot double-post;
- uncertain outcome can be resolved without replay.

IMMUTABILITY

- posted journal cannot be edited;
- posted journal cannot be deleted;
- generic CRUD cannot mutate canonical history;
- correction/reversal is additive and linked.

ATOMICITY

- failed validation produces no effect;
- line-write failure produces no partial journal;
- audit-write failure produces no successful accounting effect.

AUDIT

- successful journal has required evidence;
- evidence includes company, actor/job, capability, source, context,
  effect/idempotency identity and journal references.

BACKGROUND

- background posting requires explicit validated system/job/company context.

Use authenticated Company A/B integration fixtures where protected API routes
exist. Do not rely solely on a client-supplied company_id.
