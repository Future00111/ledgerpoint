- double-entry accounting
- balanced journals
- source-linked postings
- immutable posted accounting records
- controlled reversals/corrections
- accounting periods
- chart of accounts
- account types
- VAT/tax postings
- accounts receivable
- accounts payable
- bank/cash
- revenue
- expenses
- payments
- payment allocations
- reconciliation
- credit notes
- reporting
- audit
- idempotency
- company/tenant isolation.

The goal is NOT to build every feature now.

The goal is to establish the accounting authority that those features will use later.

==================================================
4. ACCOUNTING SOURCE OF TRUTH
==================================================

Design and explicitly define:

SOURCE TRANSACTIONS
        ↓
VALIDATION
        ↓
ACCOUNTING POSTING
        ↓
JOURNAL
        ↓
JOURNAL LINES
        ↓
ACCOUNT BALANCES
        ↓
REPORTS

The journal/posting layer must become the authoritative source for financial reporting.

Do NOT make invoices, bills, bank transactions or frontend state the authoritative source for financial reports.

Reports should ultimately derive from posted accounting entries.

==================================================
5. DOUBLE-ENTRY MODEL
==================================================

Define the canonical double-entry model.

Every posted transaction must contain:

- journal/header
- journal lines
- debit and credit amounts
- accounts
- source reference
- company
- posting date
- accounting period
- currency where applicable
- description/memo
- creation timestamp
- posting timestamp
- audit information
- idempotency key.

Enforce:

TOTAL DEBITS = TOTAL CREDITS

This must be enforced server-side.

Never trust the browser to provide the final accounting totals.

==================================================
6. JOURNAL IMMUTABILITY
==================================================

Once posted:

Journal entries must be immutable.

Do NOT allow generic UPDATE or DELETE operations against posted accounting entries.

Corrections must occur through controlled accounting mechanisms.

Examples:

Original:
DR Expense £100
CR Bank £100

Correction:

REVERSAL
DR Bank £100
CR Expense £100

Then, if appropriate, a corrected posting.

Define this properly.

Do not physically rewrite accounting history.

==================================================
7. REVERSALS AND CORRECTIONS
==================================================

Design controlled mechanisms for:

- reversal
- correction
- void/cancellation where legally/accountingly appropriate
- credit notes
- payment reversal
- duplicate correction
- period correction.

Every reversal/correction must reference the original posting.

The original journal must remain visible in the audit trail.

Never silently overwrite accounting history.

==================================================
8. IDEMPOTENCY
==================================================

Design strong idempotency protection.

The same source transaction must never create duplicate journal entries because of:

- double-click
- retry
- network failure
- worker retry
- browser refresh
- API retry
- webhook retry
- import retry
- AI retry.

Define the idempotency key strategy.

Show where the unique constraint belongs.

==================================================
9. ACCOUNTING PERIODS
==================================================

Design:

- financial year
- accounting periods
- open/closed state
- posting date
- period validation
- period closing
- controlled reopening
- audit trail.

A normal posting must not occur into a closed period.

A reopening must be a controlled privileged action and fully audited.

Define how year-end behaviour works.

Do not assume year-end automatically deletes or modifies accounting history.

==================================================
10. CHART OF ACCOUNTS
==================================================

Design the canonical chart of accounts.

At minimum support appropriate account classifications such as:

- assets
- liabilities
- equity/capital
- revenue/income
- cost of sales
- expenses
- VAT/tax
- bank/cash
- receivables
- payables.

Do not hard-code assumptions that prevent future expansion.

Define:

- account code
- account name
- account type
- parent account where appropriate
- active/inactive
- system/default account
- company ownership
- VAT/tax relationship where appropriate
- reporting classification.

Determine whether Ledgerpoint should use a default UK small-business chart of accounts with company-level customisation.

Do not implement it yet.

==================================================

Explicitly define how the accounting engine handles:

Accounts Receivable

==================================================
12. PAYMENTS AND ALLOCATIONS
==================================================

Design payment architecture so that:

Payment
≠
Payment allocation
≠
Bank transaction

These may be related but should not be incorrectly conflated.

Support:

- full payment
- partial payment
- multiple invoices
- multiple payments
- overpayment
- underpayment
- unapplied cash
- allocation changes
- payment reversal.

Every allocation must produce the correct accounting effect.

==================================================
13. BANK TRANSACTIONS
==================================================

Define how bank transactions interact with the accounting engine.

A bank transaction should not automatically become a journal merely because it was imported.

Distinguish:

BANK FEED DATA
→
RECONCILIATION / CLASSIFICATION
→
ACCOUNTING POSTING

This is important.

Imported bank data is source evidence.

Approved accounting treatment produces the authoritative posting.

Define how transfers are represented.

==================================================
16. CREDIT NOTES
==================================================

Define how credit notes will reverse/reduce:

- invoice balances
- revenue
- VAT
- AR/AP
- journals.

Ensure they never modify posted historical journal lines directly.

==================================================
17. VAT INTEGRATION
==================================================

The accounting engine must integrate with the existing deterministic VAT architecture.

DO NOT create a second VAT engine.

The posting engine should consume authoritative VAT results from the VAT service.

Define how VAT postings are represented in journals.

Example:

Sales invoice:

DR AR
CR Revenue
CR VAT Output

Purchase bill:

DR Expense
DR VAT Input
CR AP

Ensure VAT reporting can trace back to source evidence and posted journals.

==================================================
18. AUDIT TRAIL
==================================================

Every accounting posting must be traceable:

Report
→ Journal
→ Source transaction
→ User/system action
→ Timestamp
→ Approval
→ Original/reversal relationship.

Define the audit model.

Posted journals must not be deletable.

==================================================
19. COMPANY / TENANT ISOLATION
==================================================

Every accounting entity must be company scoped.

No:

- journal
- journal line
- account
- period
- payment
- allocation
- posting
- balance

may cross company boundaries.

All server-side operations must verify company membership and permissions.

==================================================
20. PERMISSIONS
==================================================

Define capabilities required for:

- viewing accounts
- creating drafts
- approving transactions
- posting
- reversing
- closing periods
- reopening periods
- editing chart of accounts
- changing accounting defaults.

Do not allow the UI alone to enforce permissions.

Server-side enforcement is mandatory.

==================================================
21. REPORTING CONTRACT
==================================================

Define how the accounting engine exposes data to reporting.

Reports should be able to derive:

- Trial Balance
- General Ledger
- Profit & Loss
- Balance Sheet
- AR
- AP
- VAT
- cash/bank
- aged debtors
- aged creditors.

Do not build the reports in this task.

Define the data contract they will consume.

==================================================
22. ROUNDING AND MONEY
==================================================

Define how Ledgerpoint handles:

- currency precision
- VAT rounding
- line-level rounding
- invoice-level rounding
- journal rounding
- zero-value lines
- tiny residuals
- balancing differences.

The system must never create an unbalanced journal because of floating-point behaviour.

Prefer integer minor units or another deterministic monetary representation.

23. DATE HANDLING
==================================================

- document date
- transaction date
- payment date
- posting date
- VAT period
- accounting period
- bank value date.

Define which date controls accounting posting.

==================================================
28. AI BOUNDARY
==================================================

The AI Accountant must never become the accounting authority.

AI may:

- recommend account
- suggest invoice match
- explain posting
- identify anomalies
- prepare a draft.

The accounting engine determines:

- whether a posting is valid
- journal balance
- VAT treatment
- period validity
- account validity
- final accounting effect.

This distinction must be explicit in the architecture.
