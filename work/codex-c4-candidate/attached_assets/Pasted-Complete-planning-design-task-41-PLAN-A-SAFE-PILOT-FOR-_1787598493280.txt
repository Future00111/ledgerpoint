# OBJECTIVE

Produce a planning/design package for a SAFE HISTORICAL ACCOUNTING MIGRATION PILOT.

The design must explain how Ledgerly could eventually migrate historical accounting data from a supported legacy source into the canonical Ledgerly accounting model without inventing accounting facts, silently changing history, creating duplicate accounting authority, or compromising tenant isolation.

The pilot must remain planning-only.

The plan must explicitly address how historical data maps into the canonical accounting foundation designed in #40.

Cover at minimum:

- canonical journals
- journal lines
- balanced double-entry invariants
- immutable posted history
- source references
- provenance
- original source identifiers
- posting dates
- financial-year assignment
- accounting-period assignment
- Chart of Accounts mapping
- DEC-10 control-account mapping
- DEC-11 configuration-version handling
- VAT treatment under DEC-03
- AR/AP history
- payments
- allocations
- customer credits
- supplier prepayments
- refunds
- bank evidence
- reconciliation evidence
- documents
- audit evidence
- retention/disposal state
- tenant/company ownership

Do not invent historical facts where the source does not provide sufficient evidence.

Unknown, ambiguous, conflicting or incomplete historical information must become explicit, auditable migration exceptions.

# IMPORTANT: NO FAKE ACCOUNTING

The design must explicitly prohibit:

- invented journals
- invented dates
- invented VAT treatment
- invented account mappings presented as historical fact
- invented allocations
- invented payments
- invented refunds
- invented period closures
- invented financial-year assignments
- invented configuration history
- invented approvals
- invented audit events
- silently guessed source provenance

Where evidence is insufficient, define an exception state and explain how that exception prevents unsafe canonicalisation.

# PILOT DESIGN

Define a conservative pilot.

- explicit source snapshot

- pre-migration backup/recovery checkpoint
- dry-run/validation before canonical persistence
- reconciliation before approval

- controlled canonical cutover
- post-cutover validation
- rollback criteria

Do not actually execute any of these.

# DUAL-READ / LEGACY AUTHORITY

DEC-22 permits bounded dual-read comparison for validation only.

Define:

- what is compared;
- for how long;
- what constitutes acceptable agreement;
- what happens when values differ;
- who investigates exceptions;
- how the canonical Ledgerly source of truth is established after cutover;
- why dual authority must not become permanent.

Legacy systems may remain read-only evidence/comparison sources where required, but they must not remain a second accounting authority after validated cutover.

# ROLLBACK

Be very precise here.

Separate:

- migration rollback before canonical cutover;
- recovery from failed migration;
- post-cutover accounting correction.

Do not propose casual deletion or rewriting of canonical accounting history.

After canonical cutover, accounting discrepancies must follow DEC-04 correction/reversal mechanisms rather than rewriting history.

# SECURITY / TENANT ISOLATION

The migration design must explicitly preserve DEC-21.

Cover:

- company-scoped migration jobs
- source-company ownership
- destination-company ownership
- background-job company context
- cross-company reference prevention
- support/break-glass access
- audit of privileged migration actions
- recovery environment isolation
- document isolation
- AI isolation if AI is used
- RLS feasibility as defence-in-depth

No unrestricted superuser migration model.

# AI

AI may assist with:

- classification suggestions
- mapping suggestions
- exception explanation
- anomaly detection

AI must NOT:

- invent accounting facts
- silently resolve ambiguity
- approve migration
- create authoritative migration decisions
- bypass deterministic validation
- bypass DEC-05 capability checks
- become the migration authority

# DEC-20 RECOVERY

Migration planning must include:

- recovery checkpoint before migration
- isolated restore testing where applicable
- integrity validation
- recovery evidence
- explicit recovery authority
- rollback decision criteria
- no silent overwrite of live accounting

# DEC-17 / DEC-18 RETENTION AND DISPOSAL

Migration must preserve applicable retention and disposal state.

It must not:

- recreate data that was legitimately disposed of;
- bypass legal holds;
- use migration as a way to circumvent DEC-18;
- lose required accounting/audit evidence.

# DEC-19 EXPORTS

If exports are used as migration inputs, distinguish:

- user-facing export
- migration extraction
- source snapshot
- canonical migration input

Do not treat a normal Ledgerly export as a backup or accounting authority.
