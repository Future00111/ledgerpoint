==================================================
APPROVED ENGINEERING DESIGN
==================================================

I explicitly approve the three selected safety mechanisms:

1. PERSISTENCE-LEVEL IMMUTABILITY

Use:

- dedicated NOLOGIN owner role:
  ledgerly_canonical_owner;
- API-role privilege separation;
- ENABLE ALWAYS PostgreSQL triggers;
- the exact protected canonical tables and transitions defined in the package.

The API role must not own the canonical tables and must not be able to UPDATE,
DELETE or TRUNCATE posted canonical accounting records.

Corrections and reversals remain additive.

Do not mutate original posted journals or lines.

2. TRANSACTIONAL FINAL FRESHNESS

Use one PostgreSQL transaction with deterministic:

SELECT ... FOR UPDATE

locking on every authoritative state required by the package.

Locks must remain held through canonical commit.

Use the exact approved lock order.

There is no ordinary-read fallback and no conditional-write fallback.

If a required provider cannot participate in the same transaction/lock
contract:

FAIL CLOSED.

Production posting must remain disabled.

3. CORRECTION / REVERSAL CONCURRENCY

Use:

- SELECT ... FOR UPDATE on the original journal;
- existing company-scoped effect/idempotency uniqueness;
- one partial unique reversal index per original journal;
- unique correction/reversal identities.

Enforce:

- at most one reversal per original journal;
- duplicate same-identity request returns the existing result;
- different identity attempting a second reversal returns deterministic conflict;
- distinct corrections serialize and proceed only if independently valid;
- original journal remains immutable.

IMMUTABILITY REQUIREMENTS
==================================================

The persistence layer must enforce:

canonical_journal_entries:
- INSERT through the canonical path only;
- UPDATE rejected;
- DELETE rejected;
- API TRUNCATE denied.

canonical_journal_lines:
- INSERT only as part of canonical journal creation;
- UPDATE rejected;
- DELETE rejected;
- API TRUNCATE denied.

canonical_journal_relations:
- additive INSERT only;
- UPDATE rejected;
- DELETE rejected;
- TRUNCATE denied.

accounting_audit_events:
- append-only INSERT;
- UPDATE rejected;
- DELETE rejected;
- TRUNCATE denied.

accounting_posting_effects:
- INSERT permitted for new effect identity;
- only approved pending → posted or pending → uncertain transition permitted;
- immutable identity/company/source/effect fields;
- all other updates rejected;
- DELETE/TRUNCATE denied.

Do not weaken these guarantees in application code.

==================================================
FRESHNESS / LOCK ORDER
==================================================

Use the approved deterministic lock order:

1. company;
2. source;
3. active membership rows sorted by ID;
4. account rows sorted by ID;
5. DEC-10 mapping rows sorted by ID;
6. DEC-11 configuration-version row;
7. financial-year row;
8. accounting-period row;
9. original journal for correction/reversal.

All relevant resolution, revalidation, posting, effect finalisation and audit
writes must use the SAME transaction handle.

Do not acquire these authoritative locks in caller-supplied order.

Lock timeout or deadlock:

- rollback;
- return RETRY_REQUIRED;
- create no partial accounting effect.

==================================================
FINAL REVALIDATION
==================================================

After locks are acquired and before canonical insert, revalidate the approved
authoritative state, including:

- source revision/evidence;
- source/company ownership;
- active membership;
- role/capability;
- account eligibility;
- DEC-10 mappings;
- DEC-11 configuration version;
- financial year;
- accounting period and period state;
- economic-effect/idempotency identity.

A mismatch must return the approved stale/conflict result and create no
canonical accounting effect.
