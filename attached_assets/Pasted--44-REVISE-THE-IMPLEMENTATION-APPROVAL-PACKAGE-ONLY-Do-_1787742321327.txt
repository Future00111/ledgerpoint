1. POSTED-JOURNAL IMMUTABILITY — SELECT ONE MECHANISM
==================================================

The package currently says database-level immutability is required but leaves
the mechanism unresolved.

Select ONE concrete mechanism.

The mechanism must guarantee that once a canonical journal is posted:

- the journal header cannot be edited;
- journal lines cannot be edited;
- the posted journal cannot be deleted;
- posted status/company/ownership cannot be altered;
- another future server-side code path cannot bypass the protection;
- corrections and reversals remain additive and do not mutate the original.

If you select database triggers, specify exactly:

- which tables;
- which operations are blocked;
- which narrowly defined transitions are permitted;
- what DDL is required;
- what schema objects are added;
- how the trigger interacts with corrections/reversals;
- how it is tested.

If you select another mechanism, provide the same level of detail.

DO NOT leave this as "trigger or equivalent".

The revised package must make ONE selection.

2. TRANSACTIONAL FRESHNESS — SELECT ONE CONCRETE MECHANISM
==================================================

The current design says "lock or conditional version check".

That is insufficient.

Select the concrete mechanism Ledgerpoint will use to guarantee that the
validated state remains valid through the canonical commit.

For each relevant state:

- source revision/evidence;
- company ownership;
- active membership/authorization;
- account eligibility;
- DEC-10 mapping;
- DEC-11 configuration version;
- financial year;
- accounting period/state;

define:

- authoritative record;
- version/revision/token;
- exact read;
- exact lock or conditional-write mechanism;
- transaction boundary;
- what concurrent change is prevented or detected;
- exact conflict result.

The design must prevent:

READ → VALIDATE → CONCURRENT CHANGE → COMMIT

from producing an unsafe posting.

DO NOT leave multiple options.
