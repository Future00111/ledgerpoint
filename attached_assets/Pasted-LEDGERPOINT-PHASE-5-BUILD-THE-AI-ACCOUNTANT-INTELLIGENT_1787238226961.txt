==================================================
1. CORE PRINCIPLE
==================================================

Ledgerpoint's AI Accountant must behave like an intelligent accounting assistant, not an unrestricted autonomous bookkeeper.

It should:

- analyse transactions
- identify likely accounting treatment
- find matching invoices and bills
- suggest nominal/account codes
- determine likely VAT treatment using the existing deterministic VAT engine
- identify anomalies
- identify missing documents
- identify duplicate transactions
- calculate confidence
- explain recommendations
- route uncertain items to human review
- learn from user decisions
- maintain an audit trail

However:

THE AI MUST NEVER SILENTLY ALTER OR POST ACCOUNTING DATA WHEN THE CONFIDENCE OR ACCOUNTING RULES DO NOT SUPPORT IT.

Deterministic accounting rules must take precedence over generative AI.

The AI may explain, rank, classify and recommend.

The deterministic accounting engine must calculate authoritative accounting/VAT values.

User approval remains the final authority for actions that require approval.

==================================================
4. TRANSACTION ANALYSIS
==================================================

For every imported bank transaction, analyse:

- transaction ID
- company
- bank account
- date
- amount
- debit/credit direction
- description
- reference
- counterparty
- existing categorisation
- linked invoice
- linked bill
- previous decisions
- VAT information where available
- duplicate indicators
- historical transaction patterns

Normalise descriptions before matching.

For example:

"STRIPE PAYOUT 12345"
"STRIPE PAYOUT REF 12345"
"STRIPE 12345 PAYOUT"

should be recognised as potentially related.

Do not rely solely on exact text matching.

==================================================
5. INVOICE MATCHING
==================================================

For incoming money, identify possible sales invoices.

For outgoing money, identify possible purchase bills.

Candidate matching should consider:

1. Exact amount
2. Near amount
3. Customer/supplier name
4. Description
5. Invoice number/reference
6. Bank reference
7. Transaction date
8. Invoice date
9. Due date
10. Historical relationship between the bank account and counterparty
11. Previously approved matching behaviour

Give each candidate a confidence score.

Example:

100%:
- exact amount
- invoice reference found
- customer name matches
- reasonable date

95%:
- exact amount
- customer matches
- date matches
- no invoice reference

75%:
- amount matches
- customer likely matches
- date reasonably close

Below configured confidence threshold:
- do not recommend automatic approval
- send to review

==================================================
7. MISSING REVENUE / MISSING INVOICE DETECTION
==================================================

This is a major Ledgerpoint feature.

When a bank receipt does not fully reconcile against available invoices, calculate:

- bank receipt amount
- matched invoice amount
- unmatched amount
- potential invoice value
- number of potential invoices
- confidence of each potential invoice

Example:

Bank receipt:
£10,000

Potential invoices:
INV-1001 £4,000
INV-1002 £3,500

Matched/potential:
£7,500

Unmatched:
£2,500

Ledgerpoint should clearly communicate:

"£2,500 of this receipt is currently unexplained."

Then show:

Potential invoices:
2

Potential invoice value:
£7,500

Unexplained amount:
£2,500

Do NOT describe the £2,500 as definitely missing revenue.

Use careful terminology such as:

"Unmatched amount"
"Unexplained receipt"
"Potential missing invoice"

because the money could represent:
- a loan
- transfer
- capital introduced
- refund
- other income
- payment on account
- multiple invoices
- timing difference

The AI should explain possible reasons.

==================================================
13. LEARNING FROM USER DECISIONS
==================================================

Ledgerpoint should learn from approved accounting decisions.

If the user repeatedly categorises:

"Amazon Business"
→
"Office supplies"

then future Amazon Business transactions should receive a higher confidence recommendation.

Store learning at company/tenant level.

Do not allow one company's learning to affect another company.

Maintain auditability.

The AI should be able to explain:

"This suggestion is based partly on 14 previously approved transactions with the same supplier."

Do not use learning to override deterministic VAT/accounting rules.

STATUS:

Do not invent VAT rates.

==================================================
15. CONFIDENCE SYSTEM
==================================================

Create a consistent confidence model.

At minimum:

95–100:
High confidence

80–94:
Strong suggestion

60–79:
Needs review

Below 60:
No reliable recommendation

However, confidence must not be based solely on the LLM.

Build confidence from deterministic signals such as:

- exact amount
- reference match
- name match
- date proximity
- historical match
- invoice status
- duplicate risk
- accounting rule compatibility

The AI may assist with semantic interpretation.

==================================================
31. NO FALSE ACCOUNTING CERTAINTY
==================================================

This is extremely important.

The AI must distinguish between:

FACT
RECOMMENDATION
POSSIBILITY
REQUIRES REVIEW

Example:

GOOD:

"£2,500 remains unmatched."

"Two invoices totalling £7,500 are potential matches."

"Possible reasons include a missing invoice or payment on account."

BAD:

"£2,500 of revenue is definitely missing."

unless the accounting data actually proves this.

Never present a guess as a fact.
